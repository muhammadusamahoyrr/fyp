# 3.5 Data Design

The Attorney.AI system transforms the complex legal information domain into a structured, scalable, and secure data architecture. This section describes the mapping of real-world legal entities into digital data structures and their subsequent storage and processing.

## 3.5.1 Transformation of Information Domain

The information domain of Attorney.AI is divided into four primary entities: Users, Intakes, Cases, and Legal Knowledge. The transformation follows a multi-layered approach:

1.  **Conceptual Layer**: Real-world legal concepts (e.g., a client filing a civil lawsuit) are defined.
2.  **Logical Layer (Pydantic Models)**: These concepts are translated into Python-based Pydantic schemas which enforce strict type validation, default values, and data integrity rules.
3.  **Physical Layer (Database Documents)**: The logical models are serialized into BSON (Binary JSON) for document-based storage or transformed into high-dimensional vectors for semantic AI processing.

## 3.5.2 Major Data Entities and Processing

| Entity | Description | Processing & Transformation |
| :--- | :--- | :--- |
| **UserDocument** | Represents clients, lawyers, and admins. | Stores role-based access data, profile info, and encrypted credentials. Lawyer profiles include vector embeddings of their specializations. |
| **IntakeDocument** | A stateful entity representing a case-in-progress during the 5-step intake. | Accumulates data across multiple sessions. Transformed into a CaseDocument once the AI analysis confirms completeness. |
| **CaseDocument** | The central unit of case management. | Contains court milestones, hearing schedules, and an "Intelligent Summary" generated by the AI engine. |
| **Milestone/Hearing** | Sub-entities for tracking case progress. | Processed as nested arrays within Case documents to maintain temporal integrity and simplify retrieval. |

## 3.5.3 Data Storage and Databases

The system utilizes a **Hybrid Database Architecture** to handle both transactional and semantic data requirements.

### 1. MongoDB (Primary Document Store)
*   **Role**: Acts as the primary source of truth for all structured and semi-structured data.
*   **Organization**: Data is organized into collections (`users`, `cases`, `intakes`, `notifications`).
*   **Benefit**: The schema-less nature allows for flexible evolution of case data as legal requirements change.

### 2. ChromaDB (Vector Database)
*   **Role**: Stores high-dimensional (384-dimension) embeddings generated by the Sentence-Transformer models.
*   **Organization**: Organized into specialized collections such as `lawyers_collection`, `judgments_collection`, and `statutes_collection`.
*   **Process**: Enables semantic similarity matching between a user's intake summary and the most relevant lawyers or legal precedents.

### 3. File System (Blob Storage)
*   **Role**: Stores raw evidence files, legal documents, and images uploaded during the intake process.
*   **Organization**: Files are organized by `case_id` or `user_id` with metadata references stored in MongoDB for quick indexing.

## 3.5.5 Detailed Data Schemas

The following sections define the primary data structures used within the system's databases in a JSON-style schema format.

### 1. UserDocument Schema (MongoDB)
```javascript
{
  _id: ObjectId,
  role: String (enum: ["CLIENT", "LAWYER", "ADMIN"]),
  email: String (required, unique),
  password_hash: String (required),
  full_name: String (required),
  phone: String (optional),
  province: String (enum: ["PUNJAB", "SINDH", "KPK", "BALOCHISTAN", "ISLAMABAD"]),
  cnic_encrypted: String (required, AES-256),
  avatar_url: String (optional),
  is_active: Boolean (default: true),
  lawyer_profile: {
    bar_number: String (optional),
    specializations: [String],
    kyc_verified: Boolean (default: false),
    rating: Number (default: 0.0),
    specialization_embedding: [Number] // 384-dim vector for semantic matching
  },
  created_at: Date,
  updated_at: Date
}
```

### 2. IntakeDocument Schema (MongoDB)
```javascript
{
  _id: ObjectId,
  session_token: String (required),
  client_id: ObjectId (ref: 'User'),
  current_step: Number (default: 1),
  completed: Boolean (default: false),
  step1: Object, // Personal info snapshot
  step2: Object, // Case categorization
  step3: Object, // Incident narrative
  step4: Object, // Document/Evidence metadata
  step5: Object, // Urgency and Outcome goals
  ai_structured_case: {
    summary: String (pending AI analysis),
    applicable_laws: [String],
    recommended_actions: [String],
    risk_level: String (enum: ["low", "medium", "high"])
  },
  case_id: ObjectId (ref: 'Case', optional),
  created_at: Date,
  updated_at: Date
}
```

### 3. CaseDocument Schema (MongoDB)
```javascript
{
  _id: ObjectId,
  case_number: String (required, unique),
  client_id: ObjectId (ref: 'User'),
  lawyer_id: ObjectId (ref: 'User', optional),
  intake_id: ObjectId (ref: 'Intake', optional),
  case_type: String (enum: ["CIVIL", "CRIMINAL", "FAMILY", "CONSTITUTIONAL"]),
  province: String (enum: ["PUNJAB", "SINDH", "KPK", "BALOCHISTAN", "ISLAMABAD"]),
  status: String (enum: ["OPEN", "IN_PROGRESS", "CLOSED"]),
  title: String (required),
  description: String (required),
  milestones: [{
    title: String,
    description: String,
    date: Date,
    completed: Boolean
  }],
  hearing_dates: [{
    date: Date,
    court: String,
    judge: String
  }],
  case_embedding: [Number], // 384-dim vector for AI-based lawyer recommendation
  created_at: Date,
  updated_at: Date
}
```

### 4. ChatSessionDocument Schema (MongoDB)
```javascript
{
  _id: ObjectId,
  session_id: String (required),
  client_id: ObjectId (ref: 'User'),
  case_id: ObjectId (ref: 'Case', optional),
  messages: [{
    role: String (enum: ["user", "assistant"]),
    content: String,
    citations: [{
      court: String,
      case_number: String,
      section: String,
      chunk_text: String
    }],
    confidence: Number,
    created_at: Date
  }],
  langgraph_checkpoint: Object, // Binary state for agentic workflow persistence
  created_at: Date,
  updated_at: Date
}
```

### 5. AgreementDocument Schema (MongoDB)
```javascript
{
  _id: ObjectId,
  title: String (required),
  body_html: String (Legal text content),
  eto_classification: String (Classification based on ETO 2002 regulations),
  parties: [{
    user_id: ObjectId (ref: 'User'),
    full_name: String,
    signed: Boolean (default: false),
    signed_at: Date,
    signature_method: String (enum: ["DIGITAL", "DRAWN", "TYPED"]),
    signature_data: String (Base64 signature image or typed name)
  }],
  status: String (enum: ["DRAFT", "PENDING", "EXECUTED", "CANCELLED"]),
  audit_log: [{
    action: String (e.g., "SIGNED", "VIEWED"),
    actor_id: ObjectId (ref: 'User'),
    timestamp: Date,
    ip_address: String,
    note: String
  }],
  created_at: Date,
  updated_at: Date
}
```

### 6. DocumentDocument Schema (MongoDB)
```javascript
{
  _id: ObjectId,
  case_id: ObjectId (ref: 'Case'),
  client_id: ObjectId (ref: 'User'),
  template_type: String (e.g., "POWER_OF_ATTORNEY", "LEGAL_NOTICE"),
  title: String (required),
  fields: Object, // Dynamic fields used to fill the template
  file_path: String (Path to generated PDF on server storage),
  status: String (enum: ["pending", "generated", "failed"]),
  created_at: Date
}
```

### 7. NotificationDocument Schema (MongoDB)
```javascript
{
  _id: ObjectId,
  user_id: ObjectId (ref: 'User'),
  type: String (e.g., "CASE_UPDATE", "NEW_MESSAGE"),
  title: String (required),
  body: String (required),
  payload: Object, // Redirect data or case references
  read: Boolean (default: false),
  read_at: Date,
  created_at: Date
}
```
